## 1. 대상과 문제가 나타나는 순간

내가 쓴 책을 갖고 싶은 로망은 있지만, 시작과 꾸준한 집필에 도움이 필요한 사람을 대상으로 한다. 이번 프로토타입은 사용자 한 명이 책 한 권을 집필하는 상황으로 제한한다.

집필 계획을 세운 뒤 일상에 밀려 약속한 일정을 잊거나, 마감이 다가와도 쓰지 못하거나, 일정을 넘겨 다시 시작하기 어려울 때 문제가 나타난다. 사용자가 직접 앱을 열 때만 확인할 수 있는 일정표로는 그 순간에 말을 걸기 어렵다.

목표는 일정 안내와 두 페르소나의 대화를 통해 사용자가 집필 상태를 확인하고, 필요한 경우 현실적인 새 일정을 약속하여 집필을 이어가도록 돕는 것이다. 책 완성률이나 습관 형성 효과가 검증됐다고 주장하지 않는다.

## 2. WhyTree 연결

이번 기능이 직접 담당하는 경로:

```text
내 책 완성
    꾸준한 집필
        집필을 잊지 않기
            계속해서 리마인드
                집필 일정 설정
```

팬과의 대화가 함께 돕는 경로:

```text
꾸준한 집필
    멈춘 뒤 다시 쓰기
        내 글을 기다리는 독자가 있다는 느낌
            독자의 응원
```

위 문구는 WhyTree의 기존 노드이며, 이 명세를 위해 새 노드를 추가하지 않는다.

## 3. 앞 단계에서 준비되어 있다고 가정하는 정보

실제 서비스의 앞 단계는 편집자와 출간기획서 인터뷰를 진행하고, 그 기획서로 목차·집필 일정·편집자 페르소나·타깃 독자 페르소나들을 만드는 과정이다. 사용자는 생성된 독자 페르소나 중 하나를 팬으로 선택한다.

이번 기능은 다음 정보를 전달받아 사용한다.

- 출간기획서와 책의 성격
- 순서가 있는 목차, 챕터별 마감일, 책의 최종 원고 마감일
- 챕터별 집필 상태
- 처음 인터뷰부터 책을 담당한 편집자의 페르소나, 이름, 소개, 사진
- 사용자가 선택한 팬의 페르소나, 이름, 소개, 사진

이번 프로토타입에서는 이 정보가 들어 있는 예시 데이터를 미리 준비한다. 기획서·목차·일정·페르소나를 생성하는 기능은 만들지 않는다. 사용자가 팬의 말투를 직접 설정하도록 요구하지 않는다. 준비된 페르소나 특성에 맞는 문구를 사용한다.

## 4. 사용자 흐름

### 4.1 처음 연결하기

1. 사용자가 자신의 책, 현재 집필 일정, 담당 편집자와 선택한 팬을 확인한다.
2. 편집자와 팬의 이름·사진·소개를 확인할 수 있다.
3. 사용자가 텔레그램의 편집자 봇과 팬 봇 각각에 대화를 시작하여 두 방을 연결한다.
4. 각 방의 첫 메시지가 역할을 소개한다. 편집자는 기획부터 함께한 담당자이고, 팬은 선택한 독자 페르소나다.
5. 자연스러운 대화로 연락받아도 되는 시간대, 편집자의 연락 시점, 팬의 연락 빈도를 정한다.
6. 앱의 스케줄 알림함을 켜고 고정된 안내 시간을 정한다. Windows 배너는 별도 브라우저 권한과 Windows 설정을 사용하며, 미허용이어도 앱 알림함은 사용할 수 있다.

### 4.2 평소 집필 중

1. 브라우저는 고정된 시간에 챕터명과 마감일 등 스케줄만 안내한다.
2. 편집자는 합의한 연락 시간에 마감 상황에 맞춰 질문한다.
3. 팬은 허용 시간대와 선택 빈도 안에서 무작위 시점에 관심·기대·응원을 표현한다.
4. 사용자가 답하면 각 역할의 페르소나에 맞는 준비된 문구와 규칙으로 대화를 이어간다.
5. 진행 상태 확인, 완료 처리, 마감 변경, 연락 빈도 조절을 대화로 수행한다.

### 4.3 일정을 지키기 어려운 경우

1. 사용자가 편집자에게 “금요일은 어려워요. 일요일로 미뤄줘”처럼 말한다.
2. 편집자가 기준 챕터와 원하는 날짜를 확인한다. 날짜나 챕터가 불분명하면 다시 묻고 변경하지 않는다.
3. 해당 챕터의 지연 일수를 계산한다.
4. 그 챕터와 이후 미완료 챕터의 마감을 같은 일수만큼 이동한 변경안을 만든다. 이미 완료한 챕터는 유지한다.
5. 변경 전후 챕터별 날짜, 전체 지연 일수, 변경된 최종 원고 마감일을 보여준다.
6. “전체 일정이 2일 늦어져 최종 마감이 11월 30일에서 12월 2일이 됩니다. 괜찮으세요?”처럼 확인한다. 날짜는 실제 일정으로 계산한다.
7. 사용자가 명확하게 동의한 경우에만 관련 일정을 한 번에 저장한다. 취소하거나 답하지 않으면 기존 일정을 유지한다.
8. 기존 예약을 갱신하여 브라우저 알림과 편집자·팬의 이후 대화가 새 일정을 기준으로 동작하게 한다.
9. 팬은 갱신된 정보를 알고 “편집자님께 일정이 이틀 늦어진다고 들었어요”처럼 반응한다. 두 봇이 서로 메시지를 주고받아야 하는 것은 아니며, 같은 확정 상태를 사용한다.

## 6. 대화와 발송 규칙

### 편집자

- 처음 책을 인터뷰하고 도와준 동일한 편집자 페르소나를 사용한다.
- 책 성격에 따른 말투는 준비된 페르소나 정보에서 가져온다.
- 예: “이번 주 금요일까지 00챕터 완료하기로 하셨죠? 잘 진행되고 있나요?”
- 예: “오늘 마감인데, 기대해도 되나요? 혹시 일정이 늦어지나요?”
- 예: “이번 원고 일정이 늦으셨네요. 언제까지 쓰실 계획인가요? 전체 일정을 미룰까요?”
- 정해진 세 마감 기준에서 연락하되, 실제 연락 시간은 사용자와 자연스러운 대화로 결정한다. 페르소나에 맞는 시간을 먼저 제안할 수 있다.
- 이미 완료한 챕터에는 남은 마감 독촉을 보내지 않는다.

### 팬

- 선택된 타깃 독자 페르소나의 특징을 말투에 반영한다.
- 예: “지난번 글 너무 좋았어요. 이번 글은 언제 나오나요?”
- 글을 실제 입력으로 받지 않은 프로토타입에서는 구체적인 원고를 읽었다는 칭찬을 임의로 만들지 않고 기대·관심 문구를 사용한다.
- 지연 중에는 “이번 이야기를 기다리고 있어요. 언제쯤 읽을 수 있을까요?”처럼 더 적극적으로 묻는다.
- 정상 상태의 빈도와 허용 시간대는 대화로 정하고 저장한다. 지연 중 하루 한 번 규칙과 정상 빈도를 별도로 유지하여 복귀할 수 있게 한다.
- 단순 응원 외에도 사용자의 답을 받아 대화를 이어가고, 일정 변경이 필요하면 편집자와 일정 확인을 이어갈 수 있게 한다. 팬이 확인 없이 전체 일정을 바꾸지 않는다.

### 상태와 시각

- 날짜 계산과 표시의 기본 기준은 한국 시간(Asia/Seoul)으로 둔다. 이는 단일 사용자 프로토타입의 구현 가정이다.
- 브라우저 고정 시각과 텔레그램 연락 허용 시간은 사용자의 대화 응답으로 정한다.
- 주간 범위 빈도의 구체적인 발송 요일·시각은 해당 기간 안에서 정하고 저장한다. 프로세스가 재시작할 때마다 새로 추첨해 발송 횟수가 달라지지 않게 한다.
- 이미 지난 마감의 사전 알림이나 완료된 챕터의 독촉을 뒤늦게 몰아서 보내지 않는다.
- 여러 챕터의 지연이 겹쳐도 팬의 지연 알림은 사용자 기준 하루 한 번으로 묶는 것을 구현 가정으로 둔다.

## 7. AI 사용 여부와 실패 대응

### 이번 버전

- 외부 AI 모델: 사용하지 않는다.
- AI API 키·AI 호출 비용: 이번 구현에는 필요하지 않다.
- 답변은 준비된 페르소나별 문구와 규칙 기반 상태 처리로 만든다. 자유로운 문장 전체를 이해하는 AI 대화가 구현되었다고 표시하지 않는다.
- 텔레그램 실제 연동에 필요한 봇 토큰은 별도다. 외부 AI를 사용하지 않는 것과 텔레그램 연결은 구분한다.

### 연결 실패·복구 시나리오

1. 시험용 응답 처리 실패를 발생시킨다. 실제 AI 장애라고 주장하지 않는다.
2. 가능한 경우 준비된 문구로 “아, 지금은 바빠요. 제가 나중에 연락드릴게요”처럼 답한다.
3. 사용자의 메시지와 처리 대기 상태를 보존한다. 확정되지 않은 일정·설정을 변경하지 않는다.
4. 복구 시 최신 일정·완료 상태·설정을 다시 읽는다.
5. 답하지 못한 마지막 메시지에서 이어서 한 번만 연락한다. 사용자에게 이미 적용된 변경을 다시 적용하지 않는다.

텔레그램 자체가 전송 불가능한 상태라면 그 채널에 즉시 기본 문구를 보낼 수는 없다. 전송 실패를 기록하고 복구 후 중복 없이 처리한다. 브라우저 알림도 권한·연결·실행 환경이 충족되지 않으면 전달 성공으로 기록하지 않는다.

### 이후 AI 연결

P2에서 연결할 모델은 미정이다. 연결 전에 모델 이름·제공자·비용·실패 처리와 데이터 전달 범위를 명세에 추가한다. AI가 제안한 변경도 사용자의 확인을 거쳐야 하며, 일정 계산·저장·예약 갱신은 검증 가능한 상태 처리로 유지한다.

## 8. 제외 범위

- 출간기획서 인터뷰 및 기획서 생성
- 목차·최초 집필 스케줄 자동 생성
- 편집자·타깃 독자 페르소나 자동 생성과 팬 선택 기능 자체
- 원고 작성·자동 수정·본격적인 편집 피드백
- 실제 AI의 자유 대화와 대화 품질 평가
- 여러 사용자·책의 동시 운영
- 문자·카카오톡 등 이번에 연결하지 않은 전달 채널
- 원고·표지·전자책·종이책 제작

페르소나 생성 기능은 제외하지만, 생성되었다고 가정한 담당 편집자와 선택된 팬의 정보·이름·사진·소개를 표시하고 활용하는 것은 P0에 포함한다.

## 9. 실행에 필요한 준비

- 텔레그램 계정, 역할별 봇 두 개, 각 봇의 토큰, 사용자의 각 봇 대화 시작이 필요하다. 봇 프로필 이름·사진·소개를 준비된 페르소나에 맞게 설정한다.
- 계속 실행되는 예약·대화 처리 프로그램과 상태 저장이 필요하다. 노트북으로 시험할 수 있지만 꺼진 동안 동작한다고 가정하지 않는다.
- 브라우저 알림을 위해 지원 브라우저, 알림 허용, 필요한 실행·보안 환경을 갖춘다. 사용자가 앱 화면을 열어 두었을 때만 가능한 방식이라면 그 한계를 명시하고 외부 예약 푸시가 된 것처럼 시연하지 않는다.
- 설치·실행·봇 연결 방법과 환경 의존성은 `prototypes/park-sunggyu/` 안의 안내에 단계별로 기록한다.
- 토큰은 비공개 환경 설정으로 관리한다. 저장소에 토큰이나 `.env`를 넣지 않는다. 루트 `.gitignore`에서 `node_modules/`와 `.env`가 제외되는지 구현 및 제출 전에 확인한다.

## 10. 사용자가 직접 할 세 가지 확인

다음 항목의 수행 상태는 문서 마지막의 최신 검증 현황과 MANUAL_CHECKS.md를 따른다. 사용자가 실제 두 텔레그램 방과 브라우저에서 확인한다. 긴 날짜를 기다리지 않도록 시험용 가까운 발송 시각을 사용할 수 있다.

### 확인 1: 전체 일정 변경과 공유

1. 서로 다른 마감일을 가진 미완료 챕터 세 개와 최종 마감일을 준비하고, 브라우저 예약 알림 도착과 두 방의 역할 구분을 확인한다.
2. 편집자에게 “이 챕터를 이틀 늦춰줘”라고 말한다.
3. 모든 관련 챕터의 변경 전후 날짜, 전체 2일 지연, 새 최종 마감일을 보여주고 동의를 묻는지 확인한다. 이 시점에는 실제 일정이 바뀌지 않아야 한다.
4. 동의하면 해당 챕터와 이후 미완료 챕터가 정확히 2일씩 한 번만 이동하는지 확인한다.
5. 기존 시각의 알림이 취소되고 새 시각의 브라우저 알림과 편집자 대화가 발생하는지 확인한다.
6. 팬이 “편집자에게 이틀 늦어진다고 들었다”는 최신 정보를 반영하는지 확인한다.

통과 기준: 명시적 동의 전 변경 없음, 날짜 계산 정확, 최종 마감 제시, 상태·예약 동시 반영, 중복 변경·발송 없음.

### 확인 2: 팬의 연락 빈도 변경과 지연 대응

1. 팬 방에서 “일주일에 한 번만 연락해”라고 말하고 설정 확인·저장을 확인한다.
2. 정상 상태에서 설정 빈도와 허용 시간대에 맞게 예약되는지 확인한다.
3. 지연 상태를 만들면 팬이 더 적극적인 말투로 하루 한 번만 연락하는지 확인한다. 편집자는 마감 다음 날 한 번만 지연 알림을 보내야 한다.
4. 새 마감을 확정하거나 챕터를 완료한 뒤 팬이 기존의 주간 빈도로 돌아가는지 확인한다.

통과 기준: 대화로 설정 변경 가능, 재시작 후 유지, 지연 중 중복 발송 없음, 정상 설정 복귀.

### 확인 3: 처리 실패 후 최신 상태로 재개

1. 시험용 응답 실패를 발생시키고 사용자 메시지에 “나중에 연락드릴게요”라는 기본 응답이 나오는지 확인한다.
2. 대기 중 다른 정상 경로로 일정을 변경하거나 해당 챕터를 완료한다.
3. 처리 기능을 복구한다.
4. 최신 상태를 알고 대화를 이어가며 과거 일정으로 독촉하지 않는지 확인한다.
5. 같은 메시지나 확인 답변을 다시 수신해도 변경과 발송이 중복되지 않는지 확인한다.

통과 기준: 대기 메시지 보존, 최신 상태 반영, 한 번만 재개, 미확정 변경이나 중복 처리 없음.

## 11. 인터뷰에서 확정된 주요 선택

- 기능 후보 중 ‘다음 집필 준비’ 대신 ‘계속해서 리마인드’를 선택했다.
- 브라우저의 단순 스케줄 안내와 텔레그램의 페르소나별 대화를 구분했다.
- 편집자·팬이 한 방에 있는 방식보다 독립된 두 방을 선택했다.
- 사용자가 말투를 직접 입력하는 방식 대신 앞 단계의 페르소나를 이어받기로 했다.
- 일정 변경은 단일 챕터만 미루는 것이 아니라 관련 목차 전체의 일정과 최종 마감을 확인받고 갱신하기로 했다.
- 지연 중 팬의 하루 두 번 발송 제안은 채택하지 않고 하루 한 번으로 정했다.
- 편집자의 지연 독촉은 매일 반복하지 않고 마감 다음 날 한 번으로 정했다.
- 실제 AI API 연결 제안은 이번에는 채택하지 않고, 준비된 문구와 규칙으로 검증한 뒤 이후 연결하기로 했다.

## 13. P0 구현에서 확정한 실행 조건

- Node.js 22 이상으로 실행하는 단일 사용자 로컬 앱을 사용한다. 코드와 실행 안내는 `prototypes/park-sunggyu/`에 둔다.
- 브라우저 알림은 이번 프로토타입에서 로컬 프로그램과 앱 탭이 켜져 있을 때 동작한다. 탭을 닫아도 전달되는 원격 Web Push와 클라우드 배포는 이번 범위에서 제외한다. 알림 권한이 거부되면 성공으로 표시하지 않는다.
- 텔레그램은 역할별 봇 두 개를 실제 Bot API로 연결한다. 토큰이 없는 동안에는 미연결 상태와 로컬 대화 연습을 제공하며, 실제 텔레그램 전달 검증과 구분한다. 토큰은 로컬 연결 화면에서 입력하고 `.env`에 보관한다.
- 이름·소개·프로필 예시 이미지는 연결 화면의 명시적 연결 동작에서 해당 봇에 적용한다. 예시 이미지는 두 가상 페르소나를 구분하는 이미지이며 실제 인물 사진이라고 주장하지 않는다.
- 텔레그램은 전송 결과를 알 수 없는 통신 오류에서 정확히 한 번 전달을 보장할 수 없다. 이런 건은 자동 재전송하지 않고 확인 필요 상태로 남겨, 이미 전달됐을 수 있는 메시지의 중복 발송을 줄인다. 확실하게 거절된 일시 오류는 지연 후 재시도한다.
- 일정 변경 제안 뒤 다른 경로에서 일정이 바뀌면 이전 제안을 그대로 확정하지 않는다. 최신 상태로 다시 제안받도록 한다.
- 정상 범위의 브라우저 알림과 실제 텔레그램 알림은 사용자가 연결·허용한 뒤 검증한다. 자동 시험이나 로컬 연습 통과를 사용자의 직접 확인으로 기록하지 않는다.

- 기존에 저장된 일정·대화·Telegram 봇 연결과 토큰은 유지하며 이 변경을 위해 프로그램을 초기화하지 않는다.

### 알림함 수정 확인 결과

별도 시험 브라우저에서 Windows 알림 권한이 기본값인 상태에서도 새 알림의 앱 알림함 도착, 읽음 처리, 새로고침 후 기록·읽음 유지가 확인됐다. 일정과 실제 Telegram 연결 상태가 바뀌지 않은 것도 확인했다. 이는 에이전트 시험이며 사용자 본인의 Windows 배너 확인을 대체하지 않는다.

## 17. 오른쪽 아래 시스템 팝업은 필수 확인 대상

- 사용자가 다시 명확히 한 요구: 앱 알림함만으로 대체하지 않고, 브라우저가 보내는 Windows 오른쪽 아래 팝업이 실제 표시되어야 한다. 알림함은 보조 기능이다.
- 일반 Edge에서 사용자가 Windows 팝업을 명시적으로 켜고 브라우저 권한을 허용하여 시험한다. Windows에서 해당 앱 알림이 비활성화되어 있으면 코드만으로 우회하지 않는다.
- 지원되는 브라우저에서는 Service Worker의 showNotification으로 시스템 알림을 요청한다. 이 작업만으로 탭을 닫은 뒤 새 예약을 수신하는 Web Push를 구현했다고 주장하지 않는다.
- 다른 탭이나 다른 브라우저가 먼저 서버의 알림을 가져갔다는 이유로 선택한 브라우저에서 팝업이 누락되지 않도록 한다. 브라우저별 표시 요청과 중복 방지를 관리한다.
- 사용자가 해당 브라우저에서 팝업을 켠 경우에만 표시 요청한다. 과거 시험 알림을 한꺼번에 다시 띄우지 않는다.
- API 요청 성공·등록된 시스템 알림과 사용자가 실제 본 Windows 배너를 구분하여 검증한다. 팝업 표시 성공은 사용자 확인 전까지 미확인이다.


## 텔레그램 고정 일정 안내와 Chrome 선택 알림 (2026-10-29)

사용자가 두 방식을 함께 선택했다. 매일 기존 일정 안내 시각(현재 한국 시간 09:00)에 텔레그램 편집자 방에도 현재 미완료 챕터와 마감을 안내한다. 편집자 마감 전·당일·다음 날 대화 및 팬의 기존 알림 규칙은 유지한다. 브라우저 알림과 텔레그램 일정 안내는 각각 켜고 끈다. 일정 변경을 확정하면 미래 안내 내용도 최신 마감으로 바꾼다. 팬 빈도 설정과 고정 일정 채널 요청을 구분하며, 대화로 변경할 때 먼저 확인을 받는다.

Chrome은 Docdall의 사이트 알림만 허용하는 방식을 선택했다. Windows의 Chrome 알림 허용과 사이트별 허용은 별개다. 기존 다른 허용 사이트는 사용자가 Chrome 알림 설정에서 제거하고 Windows Chrome 알림을 직접 켠다. 앱이 개인정보·권한 설정을 대신 바꾸지 않는다. Windows Chrome 배너의 실제 표시는 2026-10-29 사용자가 수신을 확인했다.

텔레그램은 앱 탭을 닫아도 로컬 실행 프로그램이 동작하는 동안 발송한다. 프로그램을 끄면 발송하지 않으며 지난 알림을 몰아서 보내지 않는다.

## 제출물 검사 후 수정 (2026-10-29)

- “다음 주 월요일”은 한국 시간의 월요일~일요일 주간을 기준으로 다음 주의 해당 요일을 뜻한다. 예: 2026-10-29 목요일의 다음 주 월요일은 2026-11-02이며 11월 9일이 아니다. “다음 주 일요일”도 같은 다음 주 안에서 계산한다.
- Telegram 고정 일정 안내를 켠 상태에서 연락 허용 시간대를 좁히면, 기존 고정 시각이 새 시간대 밖에 있는 경우 변경안에 새 시작 시각을 함께 제시한다. 사용자 확인 후 편집자 연락·팬 예약·고정 일정 안내를 갱신한다. 브라우저와 Telegram이 공유하는 고정 일정 시각도 함께 바뀐다고 알린다.
