# Docdall 집필 리마인드 — 박성규 P0

명세: `../../docs/specs/park-sunggyu-reminder.md`

브라우저는 고정된 시간에 집필 일정을 알린다. 텔레그램에서는 담당 편집자와 선택된 독자팬이 서로 다른 두 방에서 대화한다. 외부 AI는 연결하지 않았으며, 준비된 페르소나 문구와 규칙으로 일정·완료·연락 설정을 처리한다.

## 1. 먼저 실행하기

1. 이 폴더의 `start.cmd`를 두 번 클릭한다. Node.js 22 이상이 필요하며, 이 노트북에서는 Codex에 함께 설치된 Node 실행 파일도 찾는다.
2. 실행 창을 켜둔 채 브라우저에서 **http://localhost:3001**을 연다. 팀원의 소재 인터뷰 앱(3000번)과 다른 주소다.
3. ‘집필방 · 편집자’와 ‘집필방 · 팬’을 오가며 ‘소개 보기’를 눌러본다.
4. 사용을 마치면 실행 창에서 `Ctrl+C`를 누른다.

Node.js가 설치되어 있다면 터미널에서 이 폴더로 이동해 `node server.mjs` 또는 `npm start`로 실행할 수도 있다. 별도 패키지 설치는 필요 없다.

### 준비된 예시 입력

`fixtures/book.json`은 앞 단계에서 전달받았다고 가정한 기획서·목차·두 페르소나 정보다. 첫 실행 날짜를 기준으로 1일·4일·8일 뒤에 마감이 있는 세 챕터를 만든다. 시작 이후에는 저장된 일정을 사용한다. 기획서·목차·페르소나 생성 기능은 이번에 구현하지 않았다.

편집자 서윤과 팬 지우의 이미지도 구분을 위한 가상 예시 이미지다. 이름·소개·역할을 화면에서 확인할 수 있다. 앱 안의 대화 연습에서 확정한 변경도 같은 집필 일정에 반영된다.

## 2. 텔레그램 두 방 연결하기

봇을 만드는 이유: 각 역할이 다른 이름·프로필·대화방을 가지려면 역할별 봇 두 개가 필요하다. 두 봇은 이 로컬 프로그램을 통해 같은 집필 상태를 사용한다. 상시 클라우드 인프라나 AI API 키는 이번 시험에 필요 없다.

1. 텔레그램에서 **@BotFather**를 열고 `/newbot`을 보낸다.
2. 편집자용 봇을 하나 만든다. BotFather의 안내에 따라 이름과 고유한 사용자명을 정한다. 사용자명은 `bot`으로 끝나야 한다.
3. 같은 방법으로 팬용 봇을 하나 더 만든다. 다른 서비스가 사용하지 않는 전용 봇을 사용한다.
4. 앱의 **‘연결과 알림’**을 연다. BotFather가 발급한 각 토큰을 알맞은 역할 칸에 입력하고 **‘봇 연결·프로필 적용’**을 누른다. 토큰을 대화창이나 저장소에 붙여넣지 않는다.
5. 앱이 봇 이름·소개·예시 이미지를 적용한다. 이미지 적용을 지원하지 않거나 실패한 경우 표시되는 안내에 따라 BotFather의 `/setuserpic`으로 이 폴더의 `public/editor.jpg`, `public/fan.jpg`를 각각 올린다.
6. 각 역할 아래 생긴 **‘대화방 시작’** 링크를 누른 뒤 텔레그램에서 **시작**을 누른다. 두 역할 모두 같은 본인 텔레그램 계정을 사용한다.
7. 앱에서 두 역할이 ‘텔레그램 연결됨’으로 바뀌는지 확인한다. 일반 검색으로 봇을 찾아 시작하는 대신 앱의 연결 링크를 사용해야 본인 대화방이 등록된다.
8. 실제 텔레그램 편집자 방에서 “저녁 7시 반에 연락해줘”라고 말하고 변경안을 확인한다. 팬 방에서는 “일주일에 한 번”처럼 빈도를 정하고 확인한다.

프로그램을 끄거나 노트북이 잠들고 네트워크가 끊기면 예약·대화도 동작하지 않는다. 다른 컴퓨터까지 계속 운영하려면 이후 서버 배포가 필요하다. 기본 봇 메시지 사용에는 유료 대량 발송 기능을 사용하지 않는다.

연결 화면 대신 `.env.example`을 참고해 이 폴더의 `.env`에 `EDITOR_BOT_TOKEN`, `FAN_BOT_TOKEN`을 설정할 수도 있다. `.env`는 Git에서 제외된다. 화면·로그·상태 API에는 토큰을 반환하지 않는다.

## 3. 스케줄 알림함과 Windows 시스템 팝업

1. 화면 왼쪽의 **스케줄 알림함 켜기**를 누른다. 앱 안의 일정 알림이며 Windows 권한과 별개다.
2. 편집자 대화에서 “브라우저 알림은 오전 9시에 해줘”라고 말하고 확인한다.
3. ‘직접 확인하기’의 **스케줄 알림 5초 뒤**를 누른다.
4. 위쪽 **스케줄 알림함**에 내용과 시각이 남는지 확인한다. 읽음 표시를 하고 새로고침해도 다시 볼 수 있다.
5. 필수 시스템 팝업 시험은 일반 Edge에서 **Windows 팝업 켜기**를 누르고, 브라우저 권한과 Windows의 해당 앱 알림 설정을 사용자가 확인한다.

각 항목의 ‘앱 알림함에 저장됨’과 ‘Windows: 표시 요청됨 · 실제 표시 미확인’은 다른 상태다. 잠깐 나타나는 앱 안내를 Windows 배너 성공으로 간주하지 않는다.

앱 탭과 실행 프로그램을 열어두어야 한다. 이번 버전은 탭을 닫아도 동작하는 원격 Web Push가 아니다. Windows 배너를 사용할 수 없어도 앱 알림함은 확인할 수 있다.

## 4. 대화로 할 수 있는 일

| 말하는 예 | 동작 |
|---|---|
| “일정 보여줘” | 최신 챕터별 상태와 최종 마감 표시 |
| “이틀 미뤄줘” | 현재 미완료 챕터와 이후 미완료 챕터의 변경안 제시 |
| “2장을 2026-11-10으로 미뤄줘” | 해당 챕터부터 전체 변경안 제시 |
| “금요일은 어려워요. 일요일로 미뤄줘” | 다음 해당 요일의 새 날짜로 변경안 제시 |
| “확인” / “취소” | 대기 중인 변경안 확정 또는 취소 |
| “1장 다 썼어요” | 완료 여부 확인 후 저장·해당 챕터 독촉 중단 |
| “일주일에 한 번만 연락해” | 팬의 평소 빈도 변경안 제시 |
| “매일” / “주 2~3회” | 팬의 평소 빈도 선택 |
| “09:00~21:00에 연락해줘” | 연락 허용 시간대 변경안 제시 |
| “저녁 7시 반에 연락해줘” | 편집자 연락 시각 변경안 제시 |
| “소개해줘” | 현재 역할의 소개와 프로토타입 방식 안내 |

자유 문장을 모두 이해하지는 않는다. 모호한 요청이면 지원하는 표현을 안내하고 다시 묻는다. 팬에게 일정 변경을 요청하면 편집자에게 변경안을 확인하도록 안내한다.

### 일정 변경과 연락 기준

- 관련 챕터별 변경 전후 날짜·지연 일수·새 최종 마감을 제시하고 동의 후에만 변경한다.
- 완료된 챕터는 옮기지 않는다. 다른 경로로 상태가 바뀌면 오래된 변경안을 거절하고 최신 상태를 확인한다.
- 편집자는 마감 3일 전·당일·다음 날에 연락한다. 지연 독촉을 매일 반복하지 않는다.
- 팬은 정상 상태의 선택 빈도와 허용 시간대 안에서 무작위 시점에 연락한다. 예약은 저장되어 재시작할 때마다 달라지지 않는다.
- 지연 중 팬의 예약 연락은 하루 한 번이다. 일정 확정·완료 뒤 평소 빈도로 돌아가며, 이후 새 마감을 넘기면 다시 지연 기준을 적용한다. 사용자 대화에 대한 답장과 일정 변경 결과 안내는 예약 연락 횟수와 별개다.
- 정상 일정의 알림은 연결 및 설정을 마친 뒤 시험한다. 미연결일 때의 메시지는 앱 연습 기록이며 실제 텔레그램 발송이 아니다.

## 5. 직접 확인할 세 가지 시나리오

정확한 절차와 통과 기준은 명세의 10번 항목에 있다. 결과는 `MANUAL_CHECKS.md`에 사용자 본인이 기록한다.

1. **전체 일정 변경:** 편집자에게 이틀 미루기 요청 → 변경안 확인 전 날짜 유지 → 확인 후 모든 관련 마감 이동 → 팬의 새 일정 반영 → 변경된 예약 알림 확인.
2. **연락 빈도:** 팬에게 주 1회 요청·확인 → 저장 확인 → ‘직접 확인하기’에서 지연 시험 → 팬 하루 한 번 예약 → 새 일정 확정 또는 완료 후 평소 빈도 복귀.
3. **실패·최신 상태 복구:** 편집자 방에서 ‘응답 실패 시험’ → 메시지 보내기 → 팬 방에서 챕터 완료·확인 → 편집자 방에서 ‘복구·대화 이어가기’ → 완료된 최신 상태 반영 확인.

‘편집자 연락 5초 뒤’와 ‘팬 연락 5초 뒤’는 텔레그램에 연결되어 있으면 실제로 발송한다. 미연결이면 앱 연습에만 기록한다. 실패 시험은 실제 AI 장애가 아니라 응답 처리의 시험용 실패다.

## 6. 자동 확인

```sh
node --test test/reminder.test.mjs
```

동의 전후 일정 변경, 모호한 날짜·취소, 중복 입력, 오래된 변경안, 설정 저장, 지연 예약, 복구, 재시작, 텔레그램의 본인 대화 연결, 전송 불확실성, 로컬 HTTP 경계를 확인한다. 텔레그램 검증은 대역으로 수행하므로 **실제 봇·브라우저 직접 확인을 대체하지 않는다.**

## 7. 저장과 실패 기록

- `.data/state.json`: 예시 책의 현재 상태, 대화, 설정, 예약, 처리 기록. Git에서 제외한다.
- `.env`: 봇 토큰. Git에서 제외한다.
- 프로그램 재시작 시 상태를 복구한다. 브라우저 탭이 없거나 전송 결과가 불명확하면 전달 완료로 표시하지 않는다.
- 텔레그램 전송 결과를 모르는 통신 오류는 ‘확인 필요’로 남기고 자동 재전송하지 않는다. 이미 도착했을 수도 있으므로 실제 대화방에서 확인한다.
- 동일한 봇으로 이 프로그램을 두 개 동시에 실행하지 않는다. 포트 충돌이나 텔레그램의 중복 실행 안내가 나오면 이전 실행 창을 먼저 종료한다.

## 8. 구현 구조와 다음 범위

- `lib/core.mjs`: 한국 시간 계산, 확인 기반 상태 변경, 페르소나 문구, 일정·팬 예약, 실패·복구.
- `lib/telegram.mjs`: 역할별 실제 Bot API 연결·프로필·본인 대화 등록·수신·발송.
- `server.mjs`: 로컬 화면·상태 API·예약 실행. 기본 127.0.0.1:3001.
- `public/`: 로컬 화면과 가상 페르소나 예시 이미지.
- `fixtures/book.json`: 향후 앞 단계에서 전달받을 입력의 예시.

여러 사용자·책, 실제 AI 답변, 이메일·문자·카카오톡, 기획서 생성, 원고 편집과 대필, 클라우드 운영은 이번 구현에 포함하지 않는다. 다른 팀원의 코드나 키를 사용하지 않는다.

구현 참고: [Telegram Bot API](https://core.telegram.org/bots/api), [브라우저 Notifications API](https://developer.mozilla.org/en-US/docs/Web/API/Notifications_API).

## 9. 앱 알림함과 Windows 알림 (사용자 확인 후 수정)

- 상단의 **스케줄 알림함**에 도착한 알림 내용과 시각이 남는다. 읽음 표시와 새로고침 뒤 확인을 지원한다. 읽음은 이 브라우저의 로컬 저장소에 보관한다.
- **스케줄 알림함 켜기**는 앱 안의 일정 알림 예약을 켜는 기능이다. Windows 알림 권한이 없어도 사용할 수 있다.
- **Windows 팝업 켜기**은 별도의 사용자 동작이다. 브라우저의 권한이 허용되어도 Windows에서 해당 앱 알림이 꺼져 있으면 배너가 보이지 않을 수 있다.
- 각 알림의 ‘앱 알림함에 저장됨’과 ‘Windows: 표시 요청됨 · 실제 표시 미확인’을 구분한다. 잠깐 뜨는 안내 문구를 실제 Windows 배너 성공으로 보지 않는다.
- 앱 탭과 실행 프로그램을 열어두어야 한다. Windows 배너가 안 보일 때도 앱 알림함을 확인할 수 있다.

## 10. Windows 오른쪽 아래 시스템 팝업

- 시스템 팝업은 필수 확인 대상이며 앱 알림함으로 대체하지 않는다.
- 일반 Edge에서 http://localhost:3001 을 열고 **Windows 팝업 켜기**를 누른다. 권한 질문에 사용자가 직접 허용한다.
- ‘스케줄 알림 5초 뒤’를 눌러 실제 화면 오른쪽 아래 시스템 팝업을 확인한다. Windows에서도 해당 브라우저의 알림이 켜져 있어야 한다.
- 팝업 요청을 브라우저별로 처리하므로 Codex 내장 브라우저나 다른 탭이 먼저 같은 알림을 가져가도 선택한 Edge에서 누락되지 않는다. 같은 브라우저의 여러 탭은 공유 기록과 Web Locks로 중복 요청을 막는다.
- 지원되는 환경에서는 Service Worker의 showNotification을 사용한다. 탭을 닫은 뒤 새 예약을 받는 Web Push를 구현한 것은 아니다.
- 과거 시험 알림은 재생하지 않고, 이 브라우저에서 팝업을 켠 뒤 새로 도착한 알림을 표시한다.


## 텔레그램 고정 일정 안내와 Chrome 선택 알림 (2026-10-29)

사용자가 두 방식을 함께 선택했다. 매일 기존 일정 안내 시각(현재 한국 시간 09:00)에 텔레그램 편집자 방에도 현재 미완료 챕터와 마감을 안내한다. 편집자 마감 전·당일·다음 날 대화 및 팬의 기존 알림 규칙은 유지한다. 브라우저 알림과 텔레그램 일정 안내는 각각 켜고 끈다. 일정 변경을 확정하면 미래 안내 내용도 최신 마감으로 바꾼다. 팬 빈도 설정과 고정 일정 채널 요청을 구분하며, 대화로 변경할 때 먼저 확인을 받는다.

Chrome은 Docdall의 사이트 알림만 허용하는 방식을 선택했다. Windows의 Chrome 알림 허용과 사이트별 허용은 별개다. 기존 다른 허용 사이트는 사용자가 Chrome 알림 설정에서 제거하고 Windows Chrome 알림을 직접 켠다. 앱이 개인정보·권한 설정을 대신 바꾸지 않는다. Windows 배너의 실제 표시는 아직 사용자 확인이 필요하다.

텔레그램은 앱 탭을 닫아도 로컬 실행 프로그램이 동작하는 동안 발송한다. 프로그램을 끄면 발송하지 않으며 지난 알림을 몰아서 보내지 않는다.
